Vom Kundengespräch zur fertigen App

Wie das Prototype-First Golden Template funktioniert — in sieben Bildern.

Wir bauen zuerst einen klickbaren Prototyp, nicht zuerst ein Backend. Ein Konzept auf Papier diskutiert man drei Runden lang; ein klickbarer Prototyp beantwortet dieselben Fragen in einer. Und weil er echter Code ist, ist er kein Wegwerf-Mockup — er wird die App.

1Der Weg

Fünf Stationen. Die ersten drei laufen komplett auf erfundenen Daten — ein echtes Backend kommt erst, wenn der Kunde zugestimmt hat.

2Die zwei Achsen

Alles hängt an genau zwei Schaltern, und sie sind unabhängig: welcher Branch (Reifegrad) und welches Backend (Datenquelle). Die Matrix zeigt, was in jeder Kombination deployt wird — und wo es gar keine Kombination gibt.

3Das Branch-Modell

Zwei Promotion-Pfade, nicht ein linearer Durchlauf. Der abgestimmte Prototyp wird eingefroren und in der Produkt-Phase bewusst übersprungen — er bleibt Referenz, nicht Zwischenschritt.

4Warum der Fork nur eine Datei ist

Die App weiß nicht, woher ihre Daten kommen. Sie fragt einen Port; dahinter steckt ein austauschbarer Adapter. Die blaue Linie ist keine Bitte, sondern eine ESLint-Regel — ein Feature, das direkt einen Adapter importiert, lässt den Build rot werden.

5Die Command-Kette

Fünf Kommandos. Autonom bis dev — der einzige Punkt, an dem ein Mensch bewusst zustimmt, ist die Produktions-Promotion.

6Welcher Regelsatz gilt

Vor jedem Task liest die KI zwei Dateien immer und genau eine backend-abhängig. Der teure Fehler ist der falsche Regelsatz — eine fetch-basierte Azure-Architektur in eine CSP-gesperrte Code App bauen, oder einen gesunden Prototyp rot flaggen.

7Die fünf Pflicht-Zustände

Jede Liste und jede Detailansicht zeigt alle fünf — kein Screen ohne. Das ist der harte Teil der Definition of Done und der häufigste Grund, warum ein Prototyp zurückgeht.

8Was mechanisch erzwungen ist

Diese Regeln stehen nicht in einer Doku, die man lesen müsste — sie brechen den Build. pnpm verify läuft lokal und in CI identisch.

Kein fetch außerhalb von Adaptern Daten laufen ausschließlich über den Port @/data.
Kein localStorage/sessionStorage Der Build ist public — kein State, keine Secrets im Browser-Storage.
Kein BrowserRouter, kein Next.js/SSR Das Template ist eine statische SPA; HashRouter überlebt den Dataverse-iframe.
Layer-Grenzen Feature → Port → Adapter → Domain. Rückwärts-Imports sind Fehler.
Max. 300 Zeilen pro Datei Plus knip gegen tote Files, Exports und Dependencies.
Keine Secrets in .env Vite kompiliert jede VITE_*-Variable ins public Bundle.

Design: ausschließlich Design-Tokens (oklch, in apps/web/src/index.css) + die shadcn-Komponenten in apps/web/src/shared/components/ui/. Kein eigenes CSS-File, keine Inline-Farben. Inventar: COMPONENTS.md.

9Teilen und Deployen

Entwicklung + interner Review pnpm dev auf localhost gegen den Mock-Adapter. Nie über einen Deploy.
Kunden-Abstimmung Cloudflare-Deploy des prototype-Branches — weiterhin Mock-Daten.
Der Link entsteht über GitHub Actions Nicht jeder Commit deployt. Build-Minuten sind ein echtes Budget.
