UNIT-IX · backend: azure

Vier Dienste, eine Anfrage, eine Grenze

Wie der Azure-Stack einer UNIT-IX-App heute aussieht — und was beim Klick eines Nutzers tatsächlich passiert. Der ganze Stack besteht aus vier Pflicht-Diensten; alles Weitere kommt erst dazu, wenn es gebraucht wird.

Der Stack

Vier Dienste sind unverzichtbar. Die Auswahl fällt nicht nach Preis, sondern nach je einer Eigenschaft, die die Alternativen nicht haben.

Was bei einem Klick passiert

Sechs Schritte, zwei davon einmalig pro Sitzung. Die gestrichelte Zone links ist das Gerät des Nutzers — alles dort ist verhandelbar.

Die fünf Prüfungen am Token

Rund 45 Zeilen in apps/api/src/auth/verify.ts. Fällt eine durch, antwortet die API mit 401 und tut sonst nichts. Einzige Ausnahme: /health, damit Azure den Server prüfen kann.

  • Signatur — kommt der Ausweis von Microsoft?
  • iss — von unserem Mandanten?
  • aud — für unsere API?
  • exp — noch gültig?
  • scp — darf der Inhaber die API benutzen?

Drei Entscheidungen, die den Stack erklären

Keine Secrets Die Maschine hat einen eigenen Ausweis Der App Service meldet sich per Managed Identity an der Datenbank an. Kein DB-Passwort, deshalb kein Key Vault, deshalb nichts, was rotiert oder leaken kann. Die Identity wird nicht Server-Admin, sondern bekommt Lesen/Schreiben auf genau einer Datenbank.
Keine zweite Wahrheit Dieselbe Anmeldung lokal wie in Produktion Auch die lokale Entwicklung läuft passwortlos gegen den Azure-DEV-Server — az login statt Passwort. Es gibt im Code gar keinen zweiten Anmeldeweg, der in Produktion überraschen könnte.
Keine Kaltstarts Ein schlanker Server statt Funktionen App Service B1 mit Always On: keine Wartezeit beim ersten Aufruf, kein Container-Build, keine Registry. Auf den Server wandert nur, was aus Sicherheitsgründen dorthin muss — Fachlogik bleibt raus.

Warum Berechtigungen serverseitig liegen müssen

Der Punkt, an dem die meisten Missverständnisse hängen — und der Grund, warum die Server-Schicht der größte Aufwandsblock jedes Umzugs ist.

Im Browser — Bedienkomfort

  • ausgegraute Schaltflächen
  • ausgeblendete Menüpunkte
  • Rollen-Umschalter im Prototyp

Die App läuft auf einem Gerät, das dem Nutzer gehört. Der Ausweis liegt im Browser, und damit lassen sich mit gängigen Werkzeugen beliebige Anfragen stellen — vorbei an jeder Bildschirmmaske. Nichts hiervon verhindert einen einzigen Request.

Auf dem Server — Sicherheit

  • Trennung der Kundenfirmen — doppelt: in der API und per RLS in der DB
  • Vier-Augen-Prinzip: wer bearbeitet, gibt nicht frei
  • Audit-Trail: schreibbar, nicht änderbar, nicht löschbar

Sicherheit entsteht nur dort, wo der Nutzer nicht hinkommt. Selbst bei einem Programmierfehler in der Anwendung liefert die Datenbank keine fremden Daten aus.

Was die API heute bewusst nicht tut: Sie prüft, wer jemand ist — nicht, was er darf. Jeder angemeldete Mitarbeiter mit dem Scope access_as_user darf über die API alles. Solange alle Nutzer intern sind und ohnehin alles sehen dürfen, ist das in Ordnung. Sobald der erste Kunde „Sachbearbeiter dürfen nicht löschen“ sagt, ist das ein Feature in der API — nicht im UI.

Nebeneffekt, der sich lohnt: Holt eine Alt-App an vielen Stellen alle Datensätze und filtert erst im Browser, erledigt die RLS-Umstellung deren Absicherung automatisch — ohne dass eine einzige Abfrage angefasst werden muss. Was bleibt, ist reine Geschwindigkeit.

Umschalten zum Livegang ist ein Klick mit ein bis zwei Minuten Unterbrechung.
DEV-Umgebung · ≈ 8 € Acht Euro dafür, dass nie an Echtdaten geprobt wird So günstig, weil sie außerhalb der Arbeitszeiten abschaltet und ohne Verfügbarkeitszusage läuft. Zweiter Nutzen: sie bekommt jedes Microsoft-Update mindestens 7 Tage früher — Probleme fallen dort auf.
Betrieb 99,5 % Verfügbarkeit, 7 Tage rückwirkend Rechnerisch bis zu ~3,6 h Ausfall im Monat, real deutlich weniger. Wartung etwa monatlich, 1–2 Minuten, Fenster auf Sonntag 02:00. Datensicherung taggenau wiederherstellbar — unabhängig von Hochverfügbarkeit, die kein Backup ist.

Ehrlich bleiben muss: Der DB-Endpunkt ist öffentlich auflösbar, und die Outbound-IPs des App Service gehören der Scale Unit, nicht exklusiv dieser App. Die Absicherung trägt die Entra-only-Authentifizierung, nicht die IP-Liste. Ein Private Endpoint ist für rund 8 €/Monat nachrüstbar. Noch nicht automatisiert: Provisioning und CI/CD — letzteres dann per OIDC, nie per Client-Secret.
